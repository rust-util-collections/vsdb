## Open

### [HIGH] VerMap: an unreadable ancestor can change the result of a merge

- **Where**: `strata/src/versioned/map.rs` (`find_merge_bases`, `merge`, `rollback_to`).
- **What**: The ancestry walks use `get_commit`, which converts missing rows, decoding failures, and storage errors to `None`. When a required intermediate commit is unreadable, the merge can lose the common base even though both tips are readable. `merge` uses an empty tree when the base list is empty.
- **Why**: A disposable-store check with a missing intermediate commit confirmed that `merge` publishes the source's unchanged value over a target-only update. The prior target commit remains readable. The same lookup in `rollback_to` can misreport incomplete ancestry as `NotAncestor`.
- **Suggested fix**: Use fallible commit lookups for mutation ancestry checks and preserve the existing `Option` interface for `fork_point`. Test that an unavailable intermediate commit returns an error without advancing the target head or changing its value. No format change is needed.

### [HIGH] SlotDex: a tier-collapse read can fail after publishing a removal

- **Where**: `strata/src/slotdex/mod.rs` (`remove`, `check_generation`, `load_cached_state`).
- **What**: When removing an entry drops the last tier, `remove` commits the entry, total, and tier changes, updates the handle's generation, then counts level-zero rows using an iterator that panics on a storage error. It updates `total_cache` only after the scan.
- **Why**: The removal is visible despite the panic. If the caller catches the panic, the handle still passes the generation check with a stale cached total. A later edit through that handle can persist a wrong total. Generation checks and restore also use raw reads that panic rather than returning the storage error.
- **Suggested fix**: Compute the post-removal slot count from a fallible preflight read and install all cache changes after the commit. Use fallible reads for generation checks and hydration. Test a read failure during the last-tier transition and verify that the rows and caches still agree before and after a retry. No format change is needed.

### [MEDIUM] Namespace: failed explicit-root cleanup can discard its recovery record

- **Where**: `core/src/common/namespace.rs` (`cleanup_failed_root`, `create_with`, `reclaim_unregistered_owned_root`).
- **What**: Once rollback has durably removed the registry entry, cleanup ignores directory-read and removal errors. Both the initial rollback and a later reclaim attempt can then clear the pending-creation record while owned files remain on disk.
- **Why**: After a transient filesystem failure clears, a second `create_with` cannot recognize the residue without the pending record. The adoptability check rejects the nonempty path, and the removed namespace ID cannot be used to reclaim it.
- **Suggested fix**: Make cleanup report its outcome, retain sufficient ownership evidence across partial cleanup, and fence the removal before clearing the pending record. Test a failed removal after initialization has left artifacts, followed by a successful retry at the same path. Keep the existing checks that protect unrelated files and retired backups. No namespace format change is required.

### [MEDIUM] Migration: SlotDex converters reject valid v17 capacities above `u32::MAX`

- **Where**: `migration/src/slotdex.rs` (`convert_bytes`), `strata/src/slotdex/mod.rs` (`new`, `open_frame`), `migration/README.md` (converter table).
- **What**: v17 used the coordinate type for tier capacity, so a `SlotDex<u64, _>` or `SlotDex<u128, _>` could be created and populated with a capacity above `u32::MAX`. Both built-in logical conversion routes use the same checked narrowing to `u32`. The upgrade guide does not give these indexes a conversion route.
- **Why**: A populated fixture generated by v17.0.21 staged successfully to MMDB v5, but both the saved-ID and serialized-handle converters rejected its capacity. The entry rows survive staging; the v18 index is unavailable through the documented converters.
- **Suggested fix**: Provide a migration path that validates the legacy rows and rebuilds tier counts for a caller-selected supported capacity before publishing the new handle. Preserve the prefix, entry order, and existing v18 wire format. Document the capacity change and cover both handle forms with a v17 fixture above `u32::MAX`.

### [MEDIUM] VerMap: a failed single-key rebalance leaves unpublished pages buffered

- **Where**: `strata/src/versioned/map.rs` (`remove`, `build_root`), `strata/src/basic/persistent_btree/remove.rs` (`remove_leaf`, `fix_underflow`).
- **What**: `remove` uses the infallible tree mutation directly. A leaf removal can allocate a replacement before `fix_underflow` reads a sibling. If the sibling read fails, it panics before the cleanup used by staged builds can run.
- **Why**: A caller that catches the panic retains the previous working root along with pages and reference changes from the aborted removal. A later publication can write those unowned pages; a subsequent staged edit can also fail its empty-buffer assertion in debug builds.
- **Suggested fix**: Give the fallible VerMap mutation a checked page-read path and the same aborted-build cleanup as other working edits. Test a sibling read failure during underflow and verify the root, pending pages, and subsequent edit. Keep the standalone tree's existing convenience API and format.

### [MEDIUM] VerMap: fallible history APIs can panic while loading metadata

- **Where**: `strata/src/versioned/map.rs` (`create_branch`, `delete_branch`, `overlapping_history`), `strata/src/versioned/read.rs` (`VerMapReader::at`).
- **What**: Branch creation and deletion call infallible name or header helpers. The overlapping-history path in `head_commit` and `log` and the reader's commit lookup also use infallible raw reads.
- **Why**: An engine failure reading one of those rows panics in a `Result`-returning operation. The caller loses the engine error and its classification; for example, `VerMap::at` propagates a failed commit read while `VerMapReader::at` panics on it.
- **Suggested fix**: Share fallible row fetch and decode helpers in the `Result` paths, keeping the existing public convenience signatures. Test error propagation through the branch write preflight and the overlapping or reader history paths. No format change is needed.

### [MEDIUM] DagMap: update and prune can panic on node reads

- **Where**: `strata/src/dagmap/raw/mod.rs` (`meta`, `try_get_mut`, `links`, `prune`), `strata/src/dagmap/rawkey/mod.rs` and `strata/src/dagmap/typed.rs` (`update`).
- **What**: Both typed `update` APIs promise to report storage errors. Their fallible value lookup is preceded by a state check through `meta`, which uses panic-on-error `MapxRaw::get`. The fallible prune path also uses `meta` and panic-on-error edge and overlay scans.
- **Why**: An unreadable metadata row panics before an update's callback can run, losing the classified engine error. Prune can unwind for the same reason during its multi-step operation, leaving the caller to recover from a panic.
- **Suggested fix**: Use fallible node reads and cursors in these paths. Preserve the consumed-node guard and keep read errors distinct from stale ownership links. Test that a metadata read failure leaves the callback uncalled and that prune reports and can resume after a read failure. No format or public signature change is needed.

### [MEDIUM] VecDex: graph maintenance can panic on storage reads

- **Where**: `strata/src/vecdex/mod.rs` (`insert`, `stage_remove`, `repair_entry_point`, `compact`, `validate_store`), `strata/src/common/staged.rs` (`get_over`, `scan_prefix`).
- **What**: Mutation preflight and store validation read the graph state through `MapxRaw::get`. Removal and entry-point repair use the overlay's infallible point and range reads. `compact` uses infallible snapshot reads before rebuilding the graph.
- **Why**: A storage read failure unwinds the operation instead of returning a classified error. Earlier chunks of an `insert_batch` can already be visible. In `clone_in`, a panic from `validate_store` also bypasses cleanup of the copied prefix.
- **Suggested fix**: Use fallible graph-state, overlay, and snapshot reads in the `Result` paths. Test a storage error during a later mutation chunk and post-copy validation; check that earlier successful chunks remain visible and a failed clone is reclaimed. No format change is needed.

## Won't Fix

### [MEDIUM] platform support: memory-sizing constants overflow on 32-bit targets

- **Where**: `core/src/common/engine/mmdb.rs` (`effective_mem_budget_semantics`) and both `benches/units/legacy_budget.rs` helpers in `core` and `strata`.
- **What**: The budget test expects `64 * G` bytes in a `usize`. Both benchmark helpers use `1usize << 60` when interpreting a cgroup limit. These expressions overflow on 32-bit targets.
- **Reason**: Both expressions fit on the supported `x86_64` and `aarch64` targets. See the [platform policy](ai/compatibility-policy.md#supported-architectures).

---

### [LOW] engine: lazy-delete auto-sweep threshold stays disabled

- **Where**: `core/src/common/engine/mmdb.rs` (`mmdb_open`), MMDB `DbOptions::lazy_delete_compaction_threshold`.
- **What**: The default threshold is zero. Compaction can reclaim registered keys while their in-memory registrations survive. A restart loses registrations for rows that compaction has yet to rewrite. VSDB does not expose a namespace-level manual compaction API.
- **Reason**: Automatic sweeps rewrite populated levels even when the store has no compaction debt. Unreachable standalone B+ tree pages do not affect reads, and `PersistentBTree::gc(live_roots)` can re-register their keys after reopen. Writable VerMap recovery uses durable deletes. [MMDB sweep semantics](https://docs.rs/mmdb/5.0.1/mmdb/struct.DB.html#method.lazy_delete)

---

### [LOW] engine: budget decisions are not logged at startup
- **Where**: `core/src/common/engine/mmdb.rs` (`MEM_BUDGET`)
- **What**: Startup does not report which configuration source selected the budget. Applications can query the effective budget with `Namespace::mem_budget_bytes()` and the per-shard write buffer size with `Namespace::memory_usage()`.
- **Reason**: `vsdb_core` has no logging facade and is a library; unconditional stderr output from a storage engine is worse than silence. Revisit if a workspace-wide logging facade is adopted.

---

### [LOW] benches: fixtures and persisted state are not isolated from measured work
- **Where**: `core/benches/units/batch_write.rs`, `strata/benches/versioned.rs`, `strata/benches/units/concurrent.rs`
- **What**: Several timed closures build fixtures (fresh maps, prepopulation, rollback/discard state) or reuse a map that grows across thread-count runs. `gc_bench` starts with a clean graph because `delete_branch` already reclaimed its orphaned history. Fresh collections left unwiped grow the store during a run.
- **Reason**: The effects are on benchmark interpretation and disk usage. Isolated fixtures, per-sample resets, and benchmark-owned cleanup are a separate tooling change.
